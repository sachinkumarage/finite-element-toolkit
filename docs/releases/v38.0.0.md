# v38.0.0 — Advanced Engineering Digital Twin & Model Updating

This release adds `femtoolkit.digital_twin`: a foundational digital twin and
model-updating capability connecting measured (or, for demonstration, clearly
labeled synthetic) reference data to the existing simulation model,
calibrating selected model parameters so the simulation agrees better with
what was measured, and honestly reporting whether the update actually
improved accuracy. It answers a different question than Version 37's model
fusion (*can a cheap model and the real model be combined?*): *can the
expensive model itself be corrected to better agree with physical reality?*
Built entirely on the unmodified Version 30 simulation pipeline, Version
32/33 optimization machinery, Version 34 parallel execution, and Version 35
accuracy metrics — no new regression, search, or metric logic is duplicated.

## Added

- **`femtoolkit.digital_twin.measurements`** — `MeasurementPoint` (a measured
  value, its input conditions, an optional uncertainty, and free-form
  metadata, validated for finiteness) and `MeasurementData` (a named
  engineering quantity's ordered collection of measurement points, keyed by a
  known `femtoolkit.studies.extractors.EXTRACTORS` name, rejecting duplicate
  measurement IDs).
- **`femtoolkit.digital_twin.parameters`** — `ModelParameter` (a baseline
  value, bounds, units, an `updatable` flag, and a dotted override path) and
  `validate_unique_parameter_names`. `to_design_variable()` converts an
  updatable parameter directly into a Version 32 `DesignVariable` — the same
  bounded search every other optimization problem in this toolkit uses.
- **`femtoolkit.digital_twin.problem`** — `ModelUpdateProblem`: ties a base
  project, its parameters, and its measured data together, failing fast on
  an empty parameter list, duplicate names, no measurement points, or an
  unknown quantity name. `problem.predict(parameter_values)` runs one
  simulation per measurement point by reusing the unmodified Version 30
  `Scenario`/`apply_scenario` and Version 34 `evaluate_simulation_batch` — no
  FEA solver logic is implemented in this module.
- **`femtoolkit.digital_twin.updating`** — `ModelUpdateConfig` (a thin wrapper
  converting directly into a Version 32 `OptimizationConfig`) and
  `run_model_update`: builds a `DesignVariable` per updatable parameter and a
  picklable calibration objective evaluating the mean squared residual
  `J(theta) = (1/N) * sum((y_sim,i(theta) - y_meas,i)^2)`, then hands both to
  the unmodified Version 32/33 `OptimizationRunner`. The objective function
  stashes every measurement point's prediction into `DesignContext.metadata`
  as it runs (the same pattern Version 33's `robust.py` established),
  recovering the full prediction vector for both the baseline and the
  best-found design without a second round of simulation after the search
  finishes.
- **`femtoolkit.digital_twin.results`** — `ModelUpdateStatus`
  (`CONVERGED`/`MAX_EVALUATIONS`/`FAILED`/`INVALID`, mapped from the
  underlying Version 32/33 `StopReason`), `DigitalTwinStatus` (the engineering
  lifecycle state: `BASELINE`/`CALIBRATING`/`UPDATED`/`VALIDATED`/`FAILED`),
  and `ModelUpdateResult` — initial/updated parameters, initial/updated
  predictions, residuals before/after, a `convergence_history` (reusing
  Version 32's `OptimizationHistory.best_so_far_series` directly), and
  `to_dict()`.
- **`femtoolkit.digital_twin.validation`** — `ModelAccuracyComparison` and
  `compare_model_accuracy`: computes the unmodified Version 35
  `compute_metrics` (MAE, RMSE, R², relative error) for the baseline and the
  updated model against the same measured data, reporting `improved` as a
  plain RMSE comparison — never assumed.
- **One new example** (`examples/digital_twin/cantilever_model_updating.py`)
  — generates a synthetic measured tip displacement from a cantilever with a
  true Young's modulus of 180 GPa, calibrates a baseline guess of 200 GPa
  against it, and reports the before/after accuracy comparison.
- **A new Streamlit page** — **Digital Twin**
  (`femtoolkit.gui.workflow_pages.digital_twin_page`), one more page in the
  existing full engineering GUI consolidated in Version 37.1 (not a separate
  application): define baseline model parameters, enter a measurement
  manually or generate one synthetically (always labeled `SYNTHETIC`), run
  the baseline simulation, run model updating, and review a comparison
  section with measured-vs-simulated, residual before/after, parameter
  before/after, calibration-objective before/after, and model-update
  convergence charts.
- **Documentation** — [`docs/digital_twin.md`](../digital_twin.md): the full
  technical guide covering the engineering concept, the model-updating
  mathematics, model parameters, measurement data, the calibration search,
  validation, the cantilever example, the Streamlit page, and the scope
  boundary.

## Testing

- New `tests/digital_twin/` package (40 tests): measurements (validation,
  duplicate IDs, metadata/uncertainty round-trip), parameters (bounds
  validation, design-variable conversion, fixed-parameter rejection), problem
  (construction validation, prediction), updating (no-updatable-parameters
  `INVALID`, singular-baseline `FAILED`, true-parameter recovery, bound
  respect, fixed-parameter-never-changed — the last three marked
  `@pytest.mark.slow`), results (`to_dict`, `improved`), validation
  (accuracy comparison, worsened-accuracy honesty), and a real-FEA
  end-to-end integration test (`@pytest.mark.slow`).
- The complete regression suite passes: all tests green, zero regressions.
- `ruff check .` is clean across the full codebase, including the new GUI
  page.
- The full GUI was verified with `streamlit.testing.v1.AppTest` end to end on
  the new Digital Twin page: add a model parameter, generate a synthetic
  measurement from a true parameter value different from the baseline, run
  the baseline simulation, run model updating (converged in 5 evaluations),
  and confirm the comparison section reports improved agreement with the
  measurement — zero exceptions throughout.

## Limitations

No Bayesian calibration, machine-learning-based parameter identification,
real-time/IoT/sensor-streaming integration, state estimation, Kalman
filtering, structural health monitoring, anomaly detection, or any industrial
digital-twin platform feature (no live data connection, no cloud component, no
continuous/online updating loop). `run_model_update` calibrates against a
fixed, already-collected measurement dataset; it does not run continuously
against a live sensor feed. There is no automatic acceptance criterion for
"the update is good enough" — `compare_model_accuracy` reports the numbers;
judging whether an updated model is acceptable for a given engineering use is
left to the engineer. See the [Version 39
preview](../../README.md#roadmap) for the next planned direction (real-time
sensor integration, time-dependent digital twins, online model updating,
state estimation, Kalman filtering, advanced Bayesian calibration, structural
health monitoring, anomaly detection, and physics-informed machine learning).
